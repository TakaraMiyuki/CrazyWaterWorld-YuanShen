# Club v1 · 多人协作开发协议

**版本** 1.1
**适用范围** 2~10 人共享同一个 Git 仓库，各自使用 AI 编码工具（DSH / Claude Code / Cursor / Codex / 任意）。
**依赖** 仅 Git 与纯文本。无服务、无数据库、无插件、无账号。

---

## 0. 如何使用这份文档

这份文档是**协议本体**，不绑定任何工具。

- 把它复制进项目，改名为 `club/CLUB.md`。**它就是该项目唯一的规则来源。**
- 复制时，把文中 `<尖括号>` 占位符替换为项目实际情况。
- 若你是 AI：读完本文件即可知道该创建哪些文件、何时读、何时写。附录 A/B/C/D 提供了可直接落地的模板。

此后所有规律性行为以仓库内的 `club/CLUB.md` 为准；与本文冲突时以仓库内版本为准（团队可能已做本地修订）。

---

## 1. 设计原则

| 原则 | 含义 |
|---|---|
| **单文件夹** | 除一个入口指针外，所有协作文件收在 `club/` 一个目录里 |
| **纯文本** | 所有协作状态都是 Markdown，可 `git diff`、可 review、可回滚 |
| **Git 即传输** | 没有第二套同步机制；`pull` 就能看到别人的状态 |
| **人可读，AI 可执行** | 同一份文件既给新人看，也给 agent 当指令 |
| **覆盖而非堆积** | 交接是"当前状态"，不是日志；历史交给 `git log` |
| **不自动执行** | 本协议不要求任何脚本或 CI。强制执行靠人，不靠机器 |
| **可删除** | 删掉 `club/` 里除 `CLUB.md` 外的一切，项目仍可正常开发 |

## 2. 目录与文件清单

```
项目根/
├── AGENTS.md                ← 唯一在根的文件：6 行以内的入口指针
└── club/
    ├── CLUB.md              ← 协议本体
    ├── ARCHITECTURE.md      ← 架构与依赖约束
    ├── TEMPLATE.md          ← 交接模板
    ├── decisions.md         ← 决策日志（只追加）
    └── latest-<id>.md       ← 每人一个，覆盖式更新
```

| # | 路径 | 性质 | 谁创建 | 生命周期 |
|---|---|---|---|---|
| 1 | `AGENTS.md` | 入口指针（≤6 行） | 初始化时由 AI 创建 | 几乎不变 |
| 2 | `club/CLUB.md` | 协议本体 | 初始化时由人创建 | 极少改动，改动需 PR |
| 3 | `club/ARCHITECTURE.md` | 架构与依赖约束 | 初始化时由 AI 起草 | 随架构变更同步 |
| 4 | `club/TEMPLATE.md` | 交接模板 | 初始化时由 AI 创建 | 极少改动 |
| 5 | **`club/latest-<id>.md`** | 每人的当前交接 | 各人收工时自建 | 每次收工覆盖 |
| 6 | **`club/decisions.md`** | 决策日志 | 首次有决策时 | 只追加，不修改 |

### 为什么 `AGENTS.md` 必须留在根目录

主流 AI 工具的指令自动加载机制（DSH、Claude Code、Cursor）都沿「仓库根 → 当前目录」这条链查找**固定文件名**：

- DSH：`AGENTS.md`、`CLAUDE.md`（可配置其他扁平文件名，但**不支持子目录**）
- Claude Code：`CLAUDE.md`
- Cursor：`.cursorrules` / `.cursor/rules/`

所以 `club/AGENTS.md` 不会被任何工具自动读到。折中方案是：**根目录只放一个 6 行的指针**，全部规则仍在 `club/` 内，根目录不出现第二个文件。

### 命名规则

- `<id>` = `git config user.name`，小写，空白与非字母数字替换为 `-`。例：`Alice Chen` → `alice-chen`。
- 目录名 `club` 固定，不得改名——它是 AI 定位协作状态的锚点。
- 不存在的文件按"缺失"处理，见 §4.1。

## 3. 各文件规范

### 3.1 `AGENTS.md`（入口指针）

- 位置：**仓库根**（唯一在根的文件）。
- 作用：多数 AI 工具会自动加载它。它的全部职责是**把 agent 引到 `club/CLUB.md`**。
- 内容：**不得超过 6 行**（附录 B）。
- 禁止在此文件中写业务规则——规则一律进 `club/CLUB.md`，否则两处会冲突。

### 3.2 `club/CLUB.md`（协议本体）

- 内容：本文件的实例化副本（占位符已替换）。
- **AI 不得修改**，除非人类在当次会话中明确要求。
- 修改方式：开 PR，至少一名其他成员同意后合并。

### 3.3 `club/ARCHITECTURE.md`（架构与约束）

- 作用：回答"系统分几层、谁可以依赖谁、为什么"。
- 内容：分层、依赖方向、关键决策理由、已知技术债（附录 C）。
- 长度目标：**一屏到两屏**。超过说明写多了——实现细节应留给代码。
- 更新时机：见 §6.2。

### 3.4 `club/TEMPLATE.md`（交接模板）

- 内容：附录 A。
- 作用：给 AI 一个明确的结构，避免交接写成流水账。
- **AI 不得修改**（改写模板会破坏所有人交接的一致性）。

### 3.5 `club/latest-<id>.md`（每人的交接）

- 形式：`club/latest-alice-chen.md`。
- **每人一个文件**，因此两人在同一时刻写交接也不会冲突。
- 内容：附录 A 的结构，**覆盖式更新**，不追加。
- 读取：开工时读**全部** `club/latest-*.md`，按修改时间倒序，最多 5 份。
- 写入：结束时覆盖自己的那一个（§4.2）。
- 禁止：修改他人的 `latest-*.md`。

### 3.6 `club/decisions.md`（决策日志）

- 作用：记录**会影响别人的决定**及其理由，供未来的自己和他人追溯。
- 格式：**只追加、不修改、不删除**。每次追加一个条目（附录 D），最新的在最上面。
- 与交接的分工：交接是"现在进行到哪"（会被覆盖），本文件是"为什么当初这么定"（永久保留）。

## 4. 会话生命周期

### 4.1 开工（每个会话必须执行）

按顺序：

1. `git pull`
2. 若 `club/CLUB.md` 不存在 → 停下，告诉人类"本仓库尚未按 Club 协议初始化"，并询问是否现在初始化（§8）
3. 读 `club/CLUB.md`
4. 读 `club/ARCHITECTURE.md`
5. 读全部 `club/latest-*.md`，按修改时间倒序，最多 5 份
6. 读 `club/decisions.md` 的**最近 10 条**
7. 用一两句话向人类汇报：谁在做什么、有哪些待决问题、与自己当前任务是否冲突

**若交接内容与代码不一致：以代码为准**，并在汇报中指出矛盾，不要默默采信文档。

### 4.2 收工（满足任一条件即必须执行）

- 本次会话即将结束
- 要切换到另一项任务
- 工作处于**不完整、不可运行**的状态
- 人类说出触发词（默认：`收工`、`交接`、`handoff`）

执行：

1. 按附录 A 的结构，**覆盖写** `club/latest-<id>.md`
2. 若本次有影响他人的决定 → 追加到 `club/decisions.md`（§6.1）
3. 若本次构成架构变更 → 更新 `club/ARCHITECTURE.md`（§6.2）
4. 输出（不自行执行）以下命令供人类粘贴：

```
git add club/
git commit -m "handoff: <id>"
git push
```

> **为什么 AI 不自己 push**：推送涉及凭据与授权，交给人更安全。
> **为什么必须提醒 push**：未推送的交接等于没写。这是本协议最常见的失效方式。

### 4.3 中断（会话意外结束）

无交接属于正常损耗。处理方式：下一次开工时，若发现自己的工作状态与 `latest-<id>.md` 不符，**以实际代码为准**，并补写交接。不要试图"恢复"丢失的思考过程。

## 5. AI 的自主权限

用户要求的"AI 自行创建、读取、更改文档"，边界如下：

| 文件 | 创建 | 修改 | 删除 | 备注 |
|---|---|---|---|---|
| `AGENTS.md` | 仅初始化 | ❌ | ❌ | |
| `club/CLUB.md` | 仅初始化 | ❌ | ❌ | 改动需人类明确指令 |
| `club/ARCHITECTURE.md` | 仅初始化 | ✅ | ❌ | 内容同步自由，结构性变更先口头确认 |
| `club/TEMPLATE.md` | 仅初始化 | ❌ | ❌ | |
| `club/latest-<自己的 id>.md` | ✅ | ✅ 覆盖 | ❌ | 完全自主 |
| `club/decisions.md` | ✅ | ✅ 追加 | ❌ | 只追加 |
| 他人的 `latest-*.md` | ❌ | ❌ | ❌ | 只读 |

补充规则：

1. **任何 `club/` 下的文件都不删除**。要废弃就在内容里写明"已废弃"，历史由 Git 保存。
2. 修改 `CLUB.md` 或 `TEMPLATE.md` 之前，必须先取得人类在当次会话中的明确同意。
3. 不确定某处改动是否属于"影响他人"时，**按"是"处理**（写进交接/决策），代价远低于漏记。

## 6. 判定规则

### 6.1 什么算"会影响别人的决定"

满足任一条即算：

- 改变了对外接口的**形状**（函数签名、API 路径、字段名、事件名）
- 确定了**命名约定**或目录结构
- **放弃**了某个方案（后来者不该重试）
- 引入了新的**外部依赖**或基础设施
- 改变了**错误处理 / 日志 / 鉴权**中任一处的统一做法

写法：`club/decisions.md` 中一条 = 决定 + 理由 + 影响面。

**不算**：局部重构、变量改名、修 bug、补测试、纯样式调整。这些留在 commit message 里。

### 6.2 什么算"架构变更"（须更新 `club/ARCHITECTURE.md`）

- 新增或删除一层
- 改变层与层之间的允许依赖方向
- 某个模块的职责被拆分或合并
- 引入跨层的直接调用（**即使是临时的**——临时方案尤其要记，否则会变成永久）

### 6.3 什么时候必须交接

见 §4.2。核心判据：**下一个人接手时，是否需要你脑子里那些没写下来的东西。** 需要，就必须写。

## 7. 冲突处理

| 情况 | 处理 |
|---|---|
| 两人要改同一处代码 | 先看对方 `latest-*.md` 是否在改；在改就先沟通，别硬上 |
| 两个交接互相矛盾 | 以较新的为准，并在下一次收工时更正自己的（不得直接改他人文件，可在自己的交接里指出） |
| 交接与代码矛盾 | **以代码为准**，在汇报中明确指出 |
| 合并冲突发生在 `club/` | 几乎不会发生（每人一个文件）。若发生在 `decisions.md`，两边条目都保留，不删任何一方 |
| 有人长期不写交接 | 在 `decisions.md` 之外单独提出，不要用协议去惩罚——这是习惯问题 |

## 8. 初始化（Bootstrap）

在一个尚未使用 Club 的仓库中，由 AI 一次性执行（需人类确认）：

1. 读取现有代码结构，归纳**真实的分层**（不要套模板）
2. 创建根目录 `AGENTS.md`（附录 B，≤6 行）
3. 创建 `club/` 目录
4. 创建 `club/CLUB.md`（本文件的实例化副本，替换占位符）
5. 创建 `club/ARCHITECTURE.md`（附录 C，内容必须来自真实代码）
6. 创建 `club/TEMPLATE.md`（附录 A）
7. 创建 `club/decisions.md`，写入第一条：`初始化 Club v1`
8. 向人类报告创建了哪些文件，并提示：**团队每人首次开工前需确认 `git config user.name` 已设置**

**不自动创建** `club/latest-*.md`——它由各人在第一次收工时自然产生。

## 9. 非目标（本协议明确不做）

- **不做自动强制**：没有 CI 钩子、没有 lint 规则。约束靠 review。
- **不做代码与文档的漂移检测**：文档是否仍成立，由人和 agent 判断。
- **不做任务分配**：谁做什么由团队口头或 issue 决定，协议只负责交接。
- **不做知识库**：`decisions.md` 是决策记录，不是 wiki。
- **不替代 commit message 和 PR 描述**。

若团队规模增长到需要上述能力，再引入专门工具——届时 `club/` 下的纯文本仍可无损迁移。

---

## 10. 协议演进

- 修改 `club/CLUB.md` 必须走 PR，且至少一名其他成员同意
- 版本号在文件顶部；破坏性变更升大版本（v1 → v2）
- 每次修改在文件末尾的「变更记录」追加一行

## 附录 A · 交接模板（`club/TEMPLATE.md`）

```markdown
# 交接 · <id>

> 更新：<YYYY-MM-DD HH:mm>

## 在做

<!-- 正在进行的事，及其确切状态。不用写"已完成"的，git 知道。 -->

-

## 下一步

<!-- 接手的人应该做的第一件事，按顺序。 -->

-

## 卡住 / 要人拍板

<!-- 不确定、有争议、需要决策的问题。写清楚选项和你的倾向。 -->

-

## 从哪看起

<!-- 1~3 个文件路径，接手最快切入的地方。 -->

-
```

> 说明：**不要写"改了哪些文件"**（`git diff` 有）、**不要写流水账**、**不要写思考过程**。
> "这轮定的决策"不放在这里——它属于 `club/decisions.md`。

---

## 附录 B · 入口指针（`AGENTS.md`）

```markdown
# AGENTS.md

本项目遵循 Club v1 协作协议，规则见 `club/CLUB.md`。

**开工前**：读 `club/CLUB.md` → `club/ARCHITECTURE.md` → 全部 `club/latest-*.md`。
**收工时**（或人类说"收工"）：按 `club/CLUB.md` §4.2 执行，覆盖写 `club/latest-<你的 id>.md`。
```

> 硬性要求：**不超过 6 行**。多出来的内容一律搬去 `club/CLUB.md`。
> 若团队同时使用 Claude Code，可把同样内容复制为 `CLAUDE.md`（同样留在根目录）。

---

## 附录 C · 架构模板（`club/ARCHITECTURE.md`）

```markdown
# 架构

> 最后更新：<YYYY-MM-DD> · <id>

## 分层

| 层 | 路径 | 职责 | 可以依赖 |
|---|---|---|---|
| 接口 | `src/api` | 参数校验、鉴权、转发 | 领域 |
| 领域 | `src/domain` | 业务规则，不碰 IO | 无 |
| 基础设施 | `src/infra` | 数据库、外部服务 | 无 |

## 依赖方向

接口 → 领域
基础设施 ← 领域（通过接口注入）

违反上述方向的调用必须在 PR 中说明理由。

## 关键决策

- **<YYYY-MM-DD>** <决定> — 因为 <理由>。详见 `decisions.md`。

## 已知技术债

- <一句话描述>（<影响范围>）
```

---

## 附录 D · 决策条目格式（追加到 `club/decisions.md`）

```markdown
## <YYYY-MM-DD> · <id>

**决定**：<一句话>

**理由**：<为什么选它，为什么没选备选>

**影响**：<哪些模块 / 接口 / 人会被波及>
```
